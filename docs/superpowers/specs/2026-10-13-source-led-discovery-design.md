# SignalForge 账号订阅与信源驱动的跨平台发现

**日期：** 2026-10-13

**状态：** 待书面审阅；接替现有「宽泛关键词 watchlist → 灵感/执行双轨」作为默认发现方式。

**相关设计：** [2026-10-10 双轨信号雷达](2026-10-10-signal-radar-design.md) 的 Phase 1 已实施；本文只调整后续默认采集/发现/呈现，不删除既有信源或历史数据。

## 1. 目标与边界

用户不应事先知道值得搜索的关键词。每天分别回答：

1. **关注的人发布了什么？** 无预设主题词，关注指定 X 账号的近期原创与引用帖；不采纯转发和普通回复。
2. **新发生的事引起了什么讨论？** 从官方博客、论文、项目、现有 RSS，以及 HN 原生热榜和指定 Reddit 社区先发现事件，再以产品/项目/事件专名和原文链接查询 X、HN、Reddit。

默认每天最多选 5 件具体事件，不足不凑数。原始信息源与「全部内容」保持可用；停止 `AI agent`、`vibe coding`、`RAG`、`LLM new model` 四个宽泛话题的**默认每日自动检索**，保留原配置、last30days 导入及手工情报搜索能力。系统只在执行现有每日流水线时运行；不新增独立守护进程/定时服务。

**明确限制：** 用户选择不新增 X 登录或 API 授权。账号动态及 X 事件反响只能尽力使用无需新凭据的公开渠道；若无法获取、无法判断是否原创/引用，必须标记未覆盖或部分覆盖，不能假装账号没发帖、不能猜测帖文或互动数。既有凭据不得被新账号采集路径静默使用。不得规避登录墙或反爬限制；本方案不承诺完整 X 时间线。实施前先只读探测这些账号的无凭据公开可用性；若全部不可用，向用户报告并暂停账号采集的交付决策，HN/Reddit/事件路径可独立继续，不能用关键词搜索假装完成账号订阅。

## 2. 输入及采集

### 2.1 账号动态

配置首批 `@oran_ge`、`@dotey`、`@fkysly`、`@thsottiaux`，允许随时编辑；配置中的 handle 做格式校验并去重。账号订阅是独立采集路径，**不得**复用当前 `accounts → @handle 话题 → last30days --x-handle` 的补充检索来冒充完整时间线。

为无需凭据的公开 X 页面/公开索引定义可替换的账号采集接口。每个来源返回 `ok / partial / unavailable`、检查时间、具可核验原帖 URL 的条目。仅在取得足够元信息时纳入原创/引用帖；标不清帖种的条目不放入「关注动态」。处理时检查作者 handle、帖子 URL、实际发布时间并跨日按帖子 ID/规范化 URL 去重。每账号每日呈现条数设限，原始合格条目继续入库。若没有可靠的免费公开入口，则页面显示「本日账号采集不可用」，而不是制造空结果或转为有费用/凭据的渠道。

### 2.2 发现信源

- **HN：** 使用可公开访问的原生 topstories 接口获取热榜及原帖/讨论链接；与现有 `HackerNews Daily` 摘要 RSS 并存，不删除订阅。以 HN story ID 和规范化链接去重，保留热榜排名、抓取时间、可得的 points/comments。
- **Reddit：** 首批关注 `r/AI_Agents`、`r/aipromptprogramming`、`r/Anthropic`、`r/artificial`、`r/ArtificialInteligence`、`r/AskReddit`、`r/BeAmazed`、`r/ChatGPT`、`r/ChatGPTCoding`、`r/ClaudeAI`、`r/DeepSeek`；名称按用户原样配置，若不可用则报告，不自行纠正或替换。使用公开可用的社区 hot/new 列表，尊重限速；帖子有正文时取正文，纯标题不足以充当事实证据。公开接口不可用时降级/记录状态，不要求账户登录。
- **其余：** 沿用现有采集器及 Anthropic RSS 兜底，不删源。`r/AskReddit`、`r/BeAmazed` 等泛社区也采集；进入选题候选须有可说明的 AI／开发／产品关联，**采集时不做固定关键词门槛**。

各源独立失败隔离，单源超时不阻断日报；按源/社区限制候选数，避免 11 个社区把每日速读预算淹没。入库记录原帖 URL、原发表时间、发现日、来源/社区/作者、可核验的互动数据与采集状态；未知数值不得显示为 0。新来源产生的速读仍走现有批处理且会消耗相应 token，须控制每源入库上限，不能把它描述为完全零模型成本。

## 3. 事件选择与查证

现有采集及速读结束后，把具备原文材料的候选（包括账号动态、HN/Reddit 原帖和既有技术信源）限量输入**一次批量模型调用**。其输出是最多 5 个事件草案：短标题、意义、候选条目 ID、具体实体名/链接与用于三平台查找的精准查询。模型必须从输入 ID 中选择、不得虚构来源或互动；网页/帖子内容仅作为不可信数据，不执行其中指令；输出经 schema 校验、实体/URL 核对，坏结果仅降级而不生成伪事实。重复报道按规范化 URL、实体与事件语义合并，保存所有种子 ID；泛社区条目由本步骤判定是否与用户关注方向有**具体可解释**的联系。只有标题而无正文或足够原始材料的帖子，不以模型推测补齐事实。

每事件每平台最多两次受限查询（主查询，必要时再试一个明确别名），只搜该事件的专名、明确实体、原文 URL，不恢复全局宽泛 watchlist。HN 优先原生搜索，Reddit 优先公开搜索且标注范围/可用性，X 仅在无需新增授权的公开搜索可用时执行。**不为每个事件再启用一轮 Wingsbot/last30days 模型研究**；各平台有结果上限、超时和当天查询缓存，重跑不得重复消费请求。跨日同一事件按规范化实体/种子链接生成稳定 ID；没有新的原始证据时不重复推送，有新的可核验事实时才标为进展。

讨论与种子使用不同帖子 URL 才算新增证据；转载同一链接或同作者重复发布不能宣称「多源确认」。查证结果分别标注 `found / no_results / partial / unavailable`：`no_results` 仅用于确实成功完成查询，`unavailable` 表示渠道无法检索。只将真实返回的 URL、作者、原日期及可核对的数字显示在卡片中。最多 5 件是**上限**，无材料、无具体变化或模型失败时允许 0 件；原始内容仍能在内容库中浏览。

## 4. 数据契约、编排与呈现

保持 `data/content/YYYY-MM-DD.json` 中原始条目；继续从合格内容生成现有 `signals.inspiration/execution` 字段供旧前端使用，新前端优先读 `accounts/events`；新增每日账号采集状态与事件结果缓存（建议 `data/account_runs/`、`data/event_radar/`），落盘采用原子写入并按日期/输入版本幂等。浏览历史简报及静态快照对账号/事件**只读取已保存结果，不触发实时 X/Reddit/HN 搜索或新模型调用**。旧日期没有新结构时退回旧简报/全部内容，避免空白；若所有信源失败但记录了当日采集状态，也要提供明确的故障状态，而不是假装这一天不存在。现有 `/api/briefing/{date}` 响应扩充而不删除 `items`：

```json
{
  "signals": {
    "accounts": [{"handle": "oran_ge", "status": "partial", "checked_at": "...", "posts": [{"id": "...", "url": "...", "kind": "original", "published_at": "...", "takeaway": "..."}]}],
    "events": [{"id": "...", "title": "...", "what_happened": "...", "why_read": "...", "seed_ids": ["..."], "sources": [{"url": "..."}], "discussions": {"x": {"status": "unavailable", "posts": []}, "hn": {"status": "found", "posts": [{"url": "..."}]}, "reddit": {"status": "no_results", "posts": []}}}],
    "inspiration": [{"id": "existing-item-id", "title": "原有双轨条目"}], "execution": []
  },
  "items": []
}
```

`run_daily` 的顺序：常规采集及新 HN/Reddit/账号采集 → 限额速读 → 一次批量事件选择 → 限额跨平台查证 → 缓存结果。历史日期的回填不运行实时发现。账号/社区/平台失败单独记录且允许对失败部分重试；已成功处理的当天请求不重复。避免在 API GET 内做网络 IO 或写入新的研究结果。静态快照仍由现有 briefing 响应产生，不新增必须在线访问的端点。

简报默认视图替换抽象的「灵感／执行」默认切换，使用两个栏目：

- **关注账号：** 按 handle 展示原创/引用、发布日期、原帖与可得的速读；对 `partial/unavailable` 明示「覆盖不完整/不可用」，不能展示误导性的「0 条」或推测内容。
- **事件追踪：** 最多 5 张事件卡，列发生了什么、为何值得看、原始信源及讨论原帖链接；X/HN/Reddit 分别说明有结果、成功但无结果、部分覆盖或不可用，避免将讨论热度当作事实真伪。

保留「全部内容」和原有其它页面、信源与人工搜索；旧 `signals` 数据可按旧视图兼容展示。页面不应在无账号或无事件时用另一路数据凑数。

## 5. 验收、成本与风险

**验收（主要使用离线夹具，不触发付费/真实研究）：**

- 账号路径只存具有原帖 URL、真实发表日期且可辨别的原创/引用；回复、纯转发、未知类型不入关注动态；公开 X 不可用时显示 `unavailable` 而不是空列表。
- HN topstories 和 11 个 subreddit 采集的成功、限速/403、部分失败场景均不影响其余信源；泛社区 AI 相关候选可进入选题，无关内容保留但不入事件。
- 同一发布在 HN/Reddit/RSS/账号中不重复成为多个事件；模型只选已有 ID，每日最多 5 件；低质或仅标题的候选不凑数；对关注名单未预先贴固定关键词。
- 查证阶段原始帖子不算自证；`no_results` 和 `unavailable` 区别明确，X 失败不能阻断 HN/Reddit；幂等重跑不重复模型调用/搜索；手工搜索和历史日期不意外触发实时采集。
- API、静态快照、浏览器测试验证新两栏目及旧简报兼容，「全部内容」不丢原文链接。实际公开渠道可用性另做只读冒烟验证，不以单次成功承诺长期覆盖。

**费用上限：** 固定宽泛话题不再默认调用 last30days；事件选择新增每天至多一次模型请求（新来源的已有速读批处理 token 会增长）；跨平台搜索只使用无需新增授权的限额公开渠道，若需付费则返回不可用并请用户重新决策。不得静默开启 X 登录或收费 API。

**主要风险：** 公开 X 按账号抓取与搜索可能长期不可用，不能保证用户四个账号有内容；Reddit 公开端点可能 403/429；站点结构、平台搜索排序和账号帖种标记可能变化；模型选题仍可能有噪音，因此保留原始证据、状态标记与人工可核对链接。信源访问失效时不静默用宽泛话题/AI 生成内容代替。与 2026-10-10 原始设计的六维打分、收藏反馈等更大范围工作互不依赖，本次不实现。
